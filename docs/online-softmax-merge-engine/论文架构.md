# Online Softmax Merge 论文架构设计

## 1. 论文的核心架构主张

本文不将 online softmax merge 简单视为一个应被整体卸载的 Softmax 算子，而是从计算特征出发，将其划分为两类性质明显不同的工作负载：

1. 强依赖、低并行度、包含非线性运算的标量递推；
2. 规则、高并行度、适合向量化的数据更新。

Online softmax merge 的标量递推部分为：

\[
m^{+}=\max(m,\hat m)
\]

\[
\alpha=\exp(m-m^{+}),\qquad
\beta=\exp(\hat m-m^{+})
\]

\[
l^{+}=\alpha l+\beta\hat l
\]

\[
w*{\text{old}}=\frac{\alpha l}{l^{+}},\qquad
w*{\text{tile}}=\frac{\beta\hat l}{l^{+}}
\]

向量更新部分为：

\[
O*d^{+}
=
w*{\text{old}}O*d+
w*{\text{tile}}\hat O_d
\]

其中，标量递推具有明显的数据依赖，且包含 `max`、`exp`、乘加、倒数和权重生成等操作；向量更新则是规则的逐元素乘加。

将两部分全部交给 RVV 执行，会产生较高的逐行标量控制成本；将两部分全部交给简单的专用引擎，又会损失现有 RVV 向量流水线的吞吐优势。

因此，本文提出的核心架构思想是：

> Cluster-local SMU 负责 online softmax merge 中非线性、强依赖的标量递推，现有 Spatz RVV 流水线负责规则的向量更新。

这一设计按计算性质划分硬件边界，而不是按算子名称进行整体卸载。

---

## 2. 整体系统架构

系统由 RISC-V scalar core、Spatz RVV 单元、cluster-local Streaming Merge Unit（SMU）和共享多 bank TCDM 组成。

```text
                RISC-V Scalar Core
                ┌───────────────┐
                │ Control code  │
                │ Descriptor    │
                └───────┬───────┘
                        │ MMIO
                        ▼
┌──────────────────────────────────────────────────────────┐
│                    Spatz Vector Cluster                   │
│                                                          │
│  ┌──────────────────┐       ┌─────────────────────────┐ │
│  │ Cluster-local SMU│       │ Existing Spatz RVV Unit │ │
│  │                  │       │                         │ │
│  │ max              │       │ vector load            │ │
│  │ exp              │       │ vector multiply        │ │
│  │ normalizer       │       │ vector add             │ │
│  │ reciprocal       │       │ vector store           │ │
│  │ weight generation│       │                         │ │
│  └────────┬─────────┘       └────────────┬────────────┘ │
│           │                              │              │
│           └──────────────┬───────────────┘              │
│                          ▼                              │
│              Shared multi-bank TCDM                    │
└──────────────────────────────────────────────────────────┘
```

该架构具有三个关键特征：

1. SMU 作为 cluster-local sidecar 接入，不进入主向量流水线；
2. SMU 与 RVV 通过共享 TCDM 交换状态、权重和输出向量；
3. 软件通过 MMIO 配置 SMU，不增加新的 RISC-V 或 RVV 指令。

## 3. SMU 标量递推引擎

### 3.1 控制接口

SMU 通过 cluster-local MMIO register 或 descriptor 进行配置。建议包含以下字段：

| 字段               | 含义                            |
| ------------------ | ------------------------------- |
| `mode`             | `scalar-only` 或 `full-offload` |
| `num_rows`         | 处理行数 \(N\)                  |
| `dimension`        | 向量长度 \(D\)                  |
| `old_m_addr`       | 旧最大值地址                    |
| `old_l_addr`       | 旧归一化因子地址                |
| `tile_m_addr`      | 当前 tile 最大值地址            |
| `tile_l_addr`      | 当前 tile 归一化因子地址        |
| `output_m_addr`    | 更新后的 \(m^{+}\) 地址         |
| `output_l_addr`    | 更新后的 \(l^{+}\) 地址         |
| `old_weight_addr`  | \(w\_{\text{old}}\) 写回地址    |
| `tile_weight_addr` | \(w\_{\text{tile}}\) 写回地址   |
| `old_o_addr`       | 旧输出向量地址                  |
| `tile_o_addr`      | 当前 tile 输出地址              |
| `output_o_addr`    | 合并后输出地址                  |
| `stride`           | 行间地址跨度                    |
| `start/status`     | 启动和完成状态                  |

为降低固定启动开销，一条命令应能够处理多行数据，而不是每处理一行都重新发起 MMIO 配置。

### 3.2 标量数据路径

SMU 标量数据路径可以划分为以下阶段：

```text
Input state fetch
      ↓
Maximum selection
      ↓
Delta generation
      ↓
Exponential evaluation
      ↓
Normalizer accumulation
      ↓
Reciprocal and weight generation
      ↓
State and weight writeback
```

#### 状态读取

每行读取：

\[
m,\quad l,\quad \hat m,\quad \hat l
\]

#### 最大值更新

\[
m^{+}=\max(m,\hat m)
\]

#### 差值形成

\[
\Delta\_{\text{old}}=m-m^{+}
\]

\[
\Delta\_{\text{tile}}=\hat m-m^{+}
\]

由于 \(m^{+}\) 是两者最大值，因此两个指数输入都不大于零，有利于限制指数近似单元的输入范围。

#### 指数计算

\[
\alpha=\exp(\Delta\_{\text{old}})
\]

\[
\beta=\exp(\Delta\_{\text{tile}})
\]

指数模块可采用 LUT、分段多项式、range reduction 或 LUT 加插值等方式实现。论文的重点不是提出新的指数近似方法，而是将指数计算与完整标量 recurrence 融合为一个连续的数据流。

#### Normalizer 更新

\[
p\_{\text{old}}=\alpha l
\]

\[
p\_{\text{tile}}=\beta\hat l
\]

\[
l^{+}=p*{\text{old}}+p*{\text{tile}}
\]

#### 权重生成

\[
r=\frac{1}{l^{+}}
\]

\[
w*{\text{old}}=p*{\text{old}}r
\]

\[
w*{\text{tile}}=p*{\text{tile}}r
\]

最终写回：

\[
m^{+},\quad l^{+},\quad
w*{\text{old}},\quad w*{\text{tile}}
\]

已有实验表明，该标量数据路径的增量成本约为：

\[
20\sim22\ \text{cycles/row}
\]

因此，中大规模场景下 scalar datapath 已不再是主要性能瓶颈。

## 4. RVV 向量更新路径

SMU 生成两个 FP32 权重后，Spatz RVV 单元执行：

\[
\mathbf O^{+}
=
w*{\text{old}}\mathbf O+
w*{\text{tile}}\hat{\mathbf O}
\]

其基本数据流为：

```text
Load scalar weights
        ↓
Broadcast weights
        ↓
Vector load old O
        ↓
Vector load tile O
        ↓
Vector multiply and add
        ↓
Vector store merged O
```

示意伪代码如下：

```c
for (row = 0; row < N; row++) {
    float w0 = old_weight[row];
    float w1 = tile_weight[row];

    for (d = 0; d < D; d += VL) {
        v_old  = vle(old_o[row][d]);
        v_tile = vle(tile_o[row][d]);

        v_out = w0 * v_old + w1 * v_tile;

        vse(output_o[row][d], v_out);
    }
}
```

该方案直接复用现有 Spatz 的：

- vector decoder；
- vector register file；
- vector arithmetic pipeline；
- vector load/store unit；
- RVV 软件工具链。

因此无需修改主向量流水线，也避免在 SMU 中重复实现一个吞吐较低的简化向量处理单元。

A1 与 A2 的实验结果表明：

- 在 `(8,32)` 下，A1 比 A2 快 `1.37x`；
- 在 `(16,64)` 下，A1 比 A2 快 `2.01x`。

这说明中大规模下，复用 RVV 进行向量更新比使用当前 Full SMU vector datapath 更合理。

## 5. 双模式架构

为适应不同规模，SMU 保留两种工作模式。

### 5.1 Mode 0：Full-offload

Full-offload 模式由 SMU 完成：

- scalar recurrence；
- vector update。

该模式适合：

- 极小的 \(N\)；
- 极小的 \(D\)；
- RVV kernel 启动和 SMU-RVV handoff 成本无法被摊薄的场景。

当前 `(1,1)` 实验中，A2 相比 A1 仍快约 6%，说明极小规模下完整卸载仍具有意义。

### 5.2 Mode 1：Scalar-only

Scalar-only 模式由 SMU 完成：

- scalar recurrence；
- 更新后的 \(m^{+}\)、\(l^{+}\) 写回；
- 两个合并权重写回。

随后由 RVV 执行向量更新。

该模式适合：

- 中等和较大的 \(D\)；
- 向量工作量较多；
- RVV 高吞吐能够摊薄权重写回和 handoff 成本的场景。

因此，整体设计可以表述为一种自适应双模式 merge architecture：

```text
              ┌─────────────────────┐
              │ Runtime mode select │
              └──────────┬──────────┘
                         │
             ┌───────────┴───────────┐
             ▼                       ▼
      Full SMU mode            Scalar-only mode
      Small N and D            Medium or large D
```

模式选择可以由软件根据 \(N\)、\(D\) 和实测阈值完成，无需增加复杂的硬件预测器。

## 6. 运行时调度

运行时可以使用简单的规模感知 dispatch policy：

```c
if (N * D < threshold || D <= D_small)
    use_full_smu();
else
    use_scalar_smu_plus_rvv();
```

更准确的调度函数可写为：

\[
\text{mode}
=
f(N,D,C*{\text{startup}},T*{\text{RVV}},T\_{\text{SMU}})
\]

运行时主要完成：

1. 填写 SMU descriptor；
2. 配置 scalar-only 或 full-offload 模式；
3. 启动 SMU；
4. 在 scalar-only 模式下调用已有 RVV kernel；
5. 完成状态和输出检查。

该方法不需要修改编译器后端，也不需要定义新的 RISC-V 指令。

---

## 7. TCDM 数据组织

A1 架构依赖 SMU 与 RVV 通过 TCDM 交换状态和权重。每一行可以包含：

```text
m[row]
l[row]
tile_m[row]
tile_l[row]
old_weight[row]
tile_weight[row]
O_old[row][D]
O_tile[row][D]
O_out[row][D]
```

建议将两个权重数组分别连续存放：

```text
old_weight[0:N-1]
tile_weight[0:N-1]
```

这样：

- SMU 可以顺序写回权重；
- RVV 可以顺序加载权重；
- 软件地址生成简单；
- 数据搬运模式规则。

对于输出向量，需要考虑：

- 行首地址对齐；
- `O_old`、`O_tile` 和 `O_out` 的 bank mapping；
- stride 与 TCDM bank 数的关系；
- 避免多个数据流持续映射到同一 bank。

当前 A1 实验中，TCDM congestion 比例低于约 0.25%，说明串行执行时权重写回与 handoff 尚未构成主要瓶颈。

## 8. 当前串行执行模型

当前已经实现和验证的 A1 流程为：

```text
CPU configures SMU
        ↓
SMU processes N scalar recurrences
        ↓
SMU writes N pairs of weights
        ↓
CPU detects completion
        ↓
RVV updates N output vectors
```

总周期为：

\[
T*{\mathrm{A1}}
=
T*{\mathrm{SMU-scalar}}

- T\_{\mathrm{RVV-vector}}
  \]

该串行模式已经能够取得：

- 相比 A0 的 `1.38x` 至 `5.55x` 加速；
- 在中大规模下相比 A2 的 `1.37x` 至 `2.01x` 加速。

因此，即使尚未加入并发流水，当前架构已经能够支持论文的主要结论。

---

## 9. Producer-Consumer 并发增强

后续可以将串行 A1 扩展为行级 producer-consumer 流水：

```text
SMU computes weights for row r+1
            ||
RVV updates O vector for row r
```

需要增加：

- 双缓冲 weight slots；
- ready/valid 标志；
- 行级 FIFO；
- producer-consumer 同步；
- TCDM 访问仲裁。

执行过程可以表示为：

```text
SMU row 0 weights
        ↓
RVV row 0 update     || SMU row 1 weights
        ↓
RVV row 1 update     || SMU row 2 weights
```

串行执行的理论周期为：

\[
T*{\mathrm{serial}}
=
T*{\mathrm{scalar}}+T\_{\mathrm{vector}}
\]

加入流水后的理想周期接近：

\[
T*{\mathrm{pipeline}}
\approx
T*{\mathrm{startup}}

- N\cdot
  \max(T*{\mathrm{scalar,row}},
  T*{\mathrm{vector,row}})
  \]

该并发机制能够进一步隐藏 scalar SMU 的命令和执行开销，但在完成真实实现和实验前，应作为架构增强项或未来工作，而不能写成已经验证的贡献。

---

## 10. 不修改 ISA 和主向量流水线

本文架构不需要：

- 增加自定义 RISC-V 指令；
- 修改 scalar decoder；
- 修改 RVV decoder；
- 修改 vector instruction format；
- 修改 vector register file；
- 在每个 vector lane 中复制 exp 或 reciprocal 单元；
- 修改现有 RVV 编译和运行环境。

所需改动主要包括：

- 一个 cluster-local SMU；
- 一组 MMIO 配置寄存器；
- 一个或多个 TCDM master port；
- scalar-only/full-offload 模式控制；
- 软件驱动和 RVV update kernel。

“不修改 ISA”本身不是论文的唯一创新点，但它构成了重要的架构约束和工程价值：

1. 保持现有 RVV 软件兼容性；
2. 不影响 Spatz 主流水线关键路径；
3. SMU 可独立综合、验证和替换；
4. 集成风险和面积代价较低；
5. 可在不需要时关闭或移除。

## 11. A0、A1 和 A2 的架构意义

三种实验实现代表三种不同的体系结构选择：

| 方案 | Scalar recurrence | Vector update | 架构含义       |
| ---- | ----------------- | ------------- | -------------- |
| A0   | Software          | RVV           | 无专用卸载     |
| A1   | SMU               | RVV           | 选择性异构卸载 |
| A2   | SMU               | SMU           | 完整专用卸载   |

三者对应的设计空间为：

```text
                     Offload degree
                           ↑
                           │
         A2                │ Full recurrence offload
    SMU scalar + vector    │
                           │
         A1                │ Selective offload
    SMU scalar + RVV       │
                           │
         A0                │ No hardware offload
    Software scalar + RVV  │
                           └────────────────────────→
                              RVV reuse degree
```

论文通过比较 A0、A1 和 A2，回答以下核心问题：

> Online softmax merge 应该完全由通用向量核执行、完全由专用引擎执行，还是按照计算性质进行异构划分？

当前实验结果支持 A1：

- A0 的软件 scalar recurrence 开销过高；
- A2 的专用 vector backend 吞吐低于 RVV；
- A1 同时保留 SMU 的低标量递推成本和 RVV 的高向量吞吐。

## 12. 论文的主要架构贡献

### 12.1 Online merge 的异构工作负载分析

本文指出，online softmax merge 并不是单一性质的向量算子，而是由两类计算构成：

- dependency-heavy scalar recurrence；
- throughput-oriented vector update。

这一分析解释了为什么纯 RVV 和完整专用卸载都不一定是最优选择。

### 12.2 低侵入 cluster-local scalar merge engine

提出一个 cluster-local SMU，用于执行：

- 最大值更新；
- 双指数计算；
- normalizer 更新；
- reciprocal；
- 权重生成；
- 状态写回。

该引擎：

- 不修改 ISA；
- 不修改主向量流水线；
- 保持完整 online softmax 数值语义；
- 每行标量增量成本约为 20 至 22 cycles。

### 12.3 SMU-RVV 协同执行

提出选择性卸载数据流：

\[
\text{SMU scalar recurrence}
\rightarrow
\text{TCDM weight handoff}
\rightarrow
\text{RVV vector update}
\]

该路径在中大规模 anchor 上同时优于：

- A0：软件 scalar 加 RVV；
- A2：完整 SMU。

### 12.4 自适应卸载粒度

SMU 同时支持：

- full-offload；
- scalar-only。

运行时根据 \(N\)、\(D\) 和性能模型选择模式，从而适应不同规模的 merge 工作负载。

## 14. 最终架构定位

本文最合适的架构定位不是：

> 一个能够完整执行 online softmax merge 的专用加速器。

而是：

> 一种面向 online softmax merge 的低侵入异构协同架构：cluster-local SMU 负责非线性、强依赖的标量递推，现有 RVV 流水线负责规则向量更新，并通过双模式和运行时选择适配不同规模。

最核心的架构结论可以概括为：

> The optimal offload boundary lies between scalar recurrence and vector update: the SMU removes the dominant per-row control overhead, while the unchanged RVV pipeline preserves high per-element throughput.
