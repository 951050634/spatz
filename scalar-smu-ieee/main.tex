\title{Scalar SMU for Native Online Attention}

\author{\IEEEauthorblockN{xt}}

\begin{document}

\maketitle

\begin{abstract}
Online attention never materializes the full probability matrix; it merges
tile-local normalization and output states instead. Each merge is one logical
operation, but its computation is not uniform. A small nonlinear recurrence
updates the running maximum and normalizer and produces two rescaling weights,
and a regular $D$-dimensional vector operation applies them to the output. We
present a hardware/software co-design that specializes the recurrence alone and
leaves the vector update on the existing RISC-V Vector (RVV) datapath. A
cluster-local Scalar Online-Merge Unit (SMU) implements the recurrence in
stage-aware mixed precision: FP16 maximum and difference operations,
fixed-point exponential and reciprocal approximations, and Q16.32 normalization
accumulation. Two lightweight custom RISC-V instructions expose it.
\texttt{OMCFG} establishes workload-persistent context, \texttt{OMERGE} invokes
one recurrence, and a hardware-maintained selector tracks the alternating
scalar state.

On four native online-attention workloads, the design reaches
8.524--17.784$\times$ recurrence speedup, 4.144--6.275$\times$ merge speedup,
and 1.066--1.157$\times$ Native Core speedup over a matched software baseline.
The mixed-precision SMU also cuts standalone mapped area by 27.613\% against the
legacy scalar implementation, at cosine similarities above 0.99997 on the
native workloads. On the two anchor workloads \texttt{OMERGE} trims the
inclusive recurring recurrence/control window by 41.523--59.014\%, and
\texttt{OMCFG} trims one-time configuration cost by 33.50--35.90\%. In two
measured explicit probability-matrix cases, the same unit gives no consistent
benefit as a generic Softmax replacement.
\end{abstract}

\begin{IEEEkeywords}
RISC-V, online attention, hardware/software co-design, domain-specific
acceleration, vector processing, mixed-precision computing, Softmax.
\end{IEEEkeywords}

\section{Introduction}

Attention dominates Transformer execution: it combines high-throughput matrix
products with normalization and data-dependent nonlinearity. Matrix
multiplication has been optimized heavily, so the nonlinear and
synchronization-heavy parts now account for a larger share of the remaining
time. Online Softmax avoids holding the full normalized matrix in memory by
keeping a running maximum and normalizer as scores arrive
\cite{milakov2018online}. FlashAttention applies the same idea to tiling and
avoids materializing the complete attention matrix
\cite{dao2022flashattention}. Both reduce data movement. In exchange, the
online formulation introduces a recurrence that carries state from one score
tile to the next.

An online-attention merge contains two parts that make different demands on
hardware. The first is a small nonlinear recurrence that updates the running
maximum and normalizer and produces two rescaling weights. Maximum selection,
exponentiation, accumulation, and normalization form a dependency chain, and
the work does not grow with the output dimension $D$. The second applies the
two weights to the $D$-element partial outputs. That step is element-wise,
regular, and exposes exactly the data parallelism a vector processor is
designed for. Treating the merge as a single uniform kernel hides this
asymmetry: the state-dependent recurrence and the regular vector update suit
different execution resources.

Accelerators for attention nonlinearity have been built at several
granularities. Some add exponential or nonlinear arithmetic to a programmable
processor. Others offload the complete Softmax operator, or place a
domain-specific unit beside a RISC-V core or vector processor. Together they
show that nonlinear, dependency-heavy work rewards specialization, but they
leave a partitioning question open: how much of attention execution belongs in
dedicated hardware? Offloading the whole merge would rebuild vector
functionality that an RVV processor already provides. Leaving it all in
software keeps the state-dependent recurrence on the scalar control path.

We explore a selective alternative in the Spatz RISC-V vector cluster
\cite{Spatz2023}. A cluster-local Scalar Online-Merge Unit (SMU) accelerates
only the state-dependent recurrence; the Spatz/RVV datapath continues to
perform the $D$-dimensional output update. The SMU assigns numerical formats
per recurrence stage, according to the range and accuracy each stage needs. It
requests the shared tightly coupled data memory (TCDM) directly, so the vector
register file, the vector floating-point units, and RVV execution semantics
are untouched. Two lightweight custom RISC-V operations reduce software
orchestration. \texttt{OMCFG} establishes workload-persistent scalar context, and
\texttt{OMERGE} invokes one online recurrence. A hardware-maintained A/B selector
advances the alternating scalar state after successful completion; software
retains ownership of the dimension-dependent output buffers.

We evaluate four native online-attention workloads: N8/D32, N16/D64, N24/D64,
and N16/D128. Against a matched scalar-software recurrence that uses the same
RVV output update, the SMU speeds up the recurrence by 8.524--17.784$\times$,
the merge window by 4.144--6.275$\times$, and the Native Core by
1.066--1.157$\times$. The benefit shrinks as the measurement scope widens,
because the selective partition leaves the surrounding work unchanged. The
mixed-precision engine also cuts standalone mapped area by 27.613\% relative
to the legacy scalar implementation. On the two anchor workloads, \texttt{OMERGE}
reduces the inclusive recurring recurrence/control window by
41.523--59.014\%, and \texttt{OMCFG} cuts the one-time configuration cost by
33.50--35.90\%. The same unit gives no consistent benefit in the two measured
explicit-P cases, where it is used as a generic row-wise Softmax replacement.
That negative control supports our reading: the gain comes from matching the
hardware to the native online-attention recurrence.

We make four contributions:
\begin{itemize}
    \item We characterize the execution asymmetry within native online-attention
    merging and develop a selective HW/SW partition: a dedicated scalar engine
    handles the state-dependent recurrence, and the RVV datapath retains the
    regular $D$-dimensional output update.

    \item We design a cluster-local stage-aware mixed-precision SMU that combines
    FP16, fixed-point lookup-based nonlinear approximation, and Q16.32
    accumulation behind an FP32 memory-visible interface. It reduces standalone
    mapped area without duplicating a vector datapath.

    \item We develop a lightweight RISC-V programming model that separates
    workload-persistent configuration (\texttt{OMCFG}) from recurring execution
    (\texttt{OMERGE}), with hardware-managed scalar-state selection and
    software-managed output state.

    \item We evaluate the architecture using matched baselines across numerical
    fidelity, standalone hardware cost, native online-attention performance,
    HW/SW partitioning, and ISA-interface overhead, and use an explicit-P
    negative control to establish the applicability boundary of the proposed
    specialization.
\end{itemize}

\section{Native Online Attention and Design Motivation}

\subsection{Native Online Attention}
Attention aggregates value vectors by query-key similarity. A conventional
implementation materializes scores and normalized probabilities before
accumulating values. Online attention instead processes score tiles and updates
the normalization and output states incrementally, so the full probability
matrix is never formed. This streaming normalizer underlies online
softmax~\cite{milakov2018online} and IO-aware exact
attention~\cite{dao2022flashattention}.

For a query row, the accumulated state is represented by the triplet
\[
(m,l,\mathbf{O}).
\]
It satisfies the invariant:
\[
\begin{gathered}
m=\max_i s_i,\\
l=\sum_i \exp(s_i-m),\\
\mathbf{O}=\frac{1}{l}\sum_i \exp(s_i-m)\mathbf{v}_i.
\end{gathered}
\]
The summation covers all scores processed so far. Thus, $l$ is the softmax
denominator relative to the running maximum $m$, and $\mathbf{O}\in\mathbb{R}^{D}$
is the corresponding normalized partial output. A new score tile has state:
\[
(m_t,l_t,\mathbf{O}_t).
\]

The exact scalar merge combines the two states without reconstructing earlier
probabilities:
\begin{equation}
\label{eq:scalar_merge_recurrence}
\begin{aligned}
m' &= \max(m,m_t),\\
\tilde{l}_{\mathrm{old}} &= l\exp(m-m'), &
\tilde{l}_{\mathrm{tile}} &= l_t\exp(m_t-m'),\\
l' &= \tilde{l}_{\mathrm{old}}+\tilde{l}_{\mathrm{tile}}, &
w_{\mathrm{old}} &= \frac{\tilde{l}_{\mathrm{old}}}{l'},\quad
w_{\mathrm{tile}} = \frac{\tilde{l}_{\mathrm{tile}}}{l'}.
\end{aligned}
\end{equation}
The output state is then updated as
\[
\mathbf{O}'=w_{\mathrm{old}}\mathbf{O}
  +w_{\mathrm{tile}}\mathbf{O}_t.
\]

The first tile initializes the running state directly. Each later tile evaluates
the recurrence and updates the $D$-element output. Because the output remains
normalized, no final normalization pass is needed.

The recurrence and the vector update are logically one merge, yet they expose
different parallelism. That distinction motivates the hardware/software (HW/SW)
partition developed here.

\subsection{Execution Characteristics}
Fig.~\ref{fig:motivation} separates the merge into a state-dependent scalar
recurrence and a regular vector update. The recurrence updates $m$, $l$, and
the two weights; the vector path applies them independently to $D$ output
elements.

The recurrence limits intra-merge data parallelism. State carries across tiles,
and maximum selection, exponential rescaling, accumulation, and normalization
form a heterogeneous dependency chain. Its scalar work is independent of $D$,
so increasing $D$ adds no recurrence lanes.

Each output element $j$ obeys the opposite pattern:
\begin{equation}
\label{eq:rvv_o_update}
O'[j]=w_{\mathrm{old}}O[j]+w_{\mathrm{tile}}O_t[j],\qquad 0\leq j<D,
\end{equation}
All $D$ elements share the same weights and have no inter-element dependency.
The update is a regular floating-point multiply-add loop and maps naturally to
the existing RISC-V Vector (RVV) execution resources.

The asymmetry motivates selective specialization. Offloading the whole merge
would duplicate vector functionality. Leaving everything in software would keep
the nonlinear recurrence on the scalar path. The accelerator therefore targets
the recurrence alone; score generation, tile-local state construction, and the
$D$-dimensional output update stay programmable.

\subsection{Design Objectives}
Three objectives follow from these execution characteristics.

The first is selective specialization: dedicate hardware to the recurrence and
reuse Spatz/RVV for the regular output update. That preserves RVV
programmability without duplicating a $D$-wide datapath.

The second is a recurrence unit light enough for cluster integration. Its
stages have different numerical requirements, which motivates the stage-aware
mixed-precision design in Section~III.

The third is a HW/SW interface that separates workload-persistent context from
repeated merge invocations and keeps the alternating recurrence state in
hardware, so per-merge control traffic does not repeat.

Together they yield a fine-grained partition. A cluster-local mixed-precision
Scalar Online-Merge Unit (SMU) executes the recurrence, and the Spatz RISC-V
vector datapath performs the $D$-dimensional output update. A lightweight
RISC-V interface separates workload-persistent configuration from individual
merge invocations, and the active A/B selector for the TCDM-resident scalar
recurrence state lives in hardware. Section~III describes this architecture and
programming model.

\section{Architecture and HW/SW Co-Design}

\subsection{System Overview and HW/SW Partition}
Figure~\ref{fig:system_overview} shows how the design fits into a Spatz vector
cluster~\cite{Spatz2023}. The Snitch scalar core and the Spatz/RVV datapath
share the tightly coupled data memory (TCDM). The cluster-local SMU handles the
Section~II recurrence; Spatz/RVV keeps the regular $D$-dimensional update.

The online-merge (\texttt{OMERGE}) command follows Snitch decode, the per-core
accelerator demultiplexer, cluster issue arbiter, and \texttt{OMERGE} adapter/SMU. The
arbiter records the issuing core, and a response demultiplexer returns
completion to that owner.
Spatz/RVV instructions take the direct vector path. The SMU is an independent
TCDM requester that reads operands and writes scalar state and weights through
the shared memory. The default configuration provides 128~KiB of TCDM in 16
banks.

The integration leaves the Spatz/RVV lanes, floating-point units, vector
register file, and supported instruction semantics untouched, and introduces no
custom RVV instruction. The SMU exchanges scalar state and weights through
TCDM, so the RVV routine applies Eq.~\eqref{eq:rvv_o_update} as it is, with no
$D$-wide SMU datapath.

Query, key, and value (Q/K/V) data and working buffers are prepared before the
timed Native Core region. The region excludes allocation, input generation,
diagnostics, Q/K/V loading, and linear projection. It includes score tiles,
local states, first-tile initialization, later merges, RVV updates, and the
final output copy.
The first tile copies $(m_t,l_t,\mathbf{O}_t)$ into the running state. Each later
\texttt{OMERGE} reads the active $m,l$ and tile-local $m_t,l_t$, writes $m',l'$ to the
inactive A/B buffers, and writes both weights to TCDM. The adapter returns status
to the issuing core and commits the A/B selector when a successful response is
accepted; errors leave it unchanged. Spatz/RVV then reads the weights and
updates the output vectors, after which software advances the output pointers.
Detailed configuration, invocation, and selector semantics appear in
Sections~III-C--III-E.

Thus, the SMU handles only the scalar recurrence; software and Spatz/RVV retain
score generation, local-state construction, output addressing and update,
first-tile initialization, and the final copy.

\subsection{Stage-Aware Mixed-Precision SMU}
The SMU assigns precision per stage, because maximum selection, exponential
rescaling, accumulation, reciprocal evaluation, and weight generation span
different numerical ranges. The assignment is static and shown in
Fig.~\ref{fig:smu_datapath}; input values never select precision at runtime.
What the SMU computes is a stage-quantized approximation of the exact
recurrence in Eq.~\eqref{eq:scalar_merge_recurrence}, not exact FP32
arithmetic. A hat marks a value after a hardware conversion. The TCDM
interface carries $m$, $m_t$, $l$, and $l_t$ in FP32; the maxima and their
difference use FP16 round-to-nearest-even (RNE):
\[
\begin{aligned}
\widehat{m} &= \operatorname{RNE}_{16}(m), &
\widehat{m}_t &= \operatorname{RNE}_{16}(m_t),\\
\widehat{m}' &= \max(\widehat{m},\widehat{m}_t), &
\widehat{\Delta}_{\mathrm{old}} &= \widehat{m}-\widehat{m}',\\
\widehat{\Delta}_{\mathrm{tile}} &= \widehat{m}_t-\widehat{m}'.
\end{aligned}
\]

The exponential (EXP) stage uses one 256-entry signed Q1.14 lookup table (LUT)
over $[-8,0]$ with direct bin selection and no interpolation. The winning
contribution bypasses the LUT and returns exact unity; equal converted maxima
therefore yield unity on both paths. Only the losing difference accesses the
LUT; differences below $-8$ saturate to zero. Denote the factors by
$\widehat{s}_{\mathrm{old}}$ and
$\widehat{s}_{\mathrm{tile}}$.

The SMU converts FP32 $l$ and $l_t$ to 48-bit unsigned Q16.32 carriers,
denoted $\widehat{l}$ and $\widehat{l}_t$, and computes
\[
\widehat{l}'=\widehat{l}\,\widehat{s}_{\mathrm{old}}
            +\widehat{l}_t\,\widehat{s}_{\mathrm{tile}}
\quad\text{in Q16.32}.
\]
The denominator crosses an FP16 RNE boundary before reciprocal evaluation. A
256-entry unsigned Q1.15 LUT approximates the normalized mantissa, followed by
piecewise-linear interpolation and exponent correction. Each scaled numerator
also crosses the FP16 RNE boundary and returns to Q16.32 before weight
computation. One shared 48$\times$16 multiplier produces the old and tile
weights sequentially. The reciprocal-LUT path is selected by the
\texttt{ONLINE\_MERGE\_MIXED\_RECIPROCAL} build definition; its provenance is
reported with the evaluation results.

The engine encodes $\widehat{m}'$ and $\widehat{l}'$ as FP32 for TCDM writeback.
The encoding restores the memory-side carrier, not the precision already
discarded: the maximum comes from FP16 rounding and the normalization term from
Q16.32. Weights are rounded to FP16, widened to FP32, and consumed by the
unchanged FP32 Spatz/RVV update. FP32 therefore carries memory-visible state,
Q16.32 carries normalization range, and FP16 plus fixed-point lookup hardware
handles the bounded nonlinear stages. All assignments are fixed at design time.

through the same owner-tracked response path as the other offloaded

\texttt{OMERGE} carries no recurrence operands in the scalar register file.
The fixed \texttt{rs1} and \texttt{rs2} fields both name \texttt{x0}; the
adapter obtains the running and tile-local \texttt{m/l} operands from the
TCDM addresses in the configured context. The command carries no
$D$-dimensional output data. The adapter fixes the engine to Mixed Scalar mode
and uses the same SMU arithmetic as the matched MMIO path; the RVV routine
handles the output vector.

The destination field carries completion status. When Snitch accepts an
\texttt{OMERGE}, it reserves \texttt{rd} in the accelerator scoreboard and
passes the instruction and request identifier through the cluster issue path.
The adapter then advances through its one-outstanding-command sequence:
\texttt{IDLE}, \texttt{START}, \texttt{WAIT}, and \texttt{RESP}. In
\texttt{WAIT}, the adapter waits for the SMU to report DONE or ERROR. In
\texttt{RESP}, the existing accelerator response channel returns the request
identifier and status data to the issuing core. The core writes that data to
\texttt{rd} and clears the pending destination when it accepts the response.
Status zero denotes successful completion; a nonzero status denotes an error.
Thus, software observes a completed instruction only after the accelerator
response reaches the core.

\texttt{OMERGE} removes repeated launch control from the recurring merge path.
The legacy MMIO path performs context traffic, launch, and completion checks
around each recurrence. The instruction path keeps persistent context in the
shared canonical configuration registers and represents each later recurrence
with one command. In the evaluation, any recurring-interface measurement is
treated as an inclusive recurrence/control window and is not interpreted as
pure dispatch latency; it includes issue, SMU execution, response commit, and
status consumption.

The instruction completes the scalar part of a merge. After a zero status, the
existing RVV routine reads $w_{\mathrm{old}}$ and $w_{\mathrm{tile}}$ from TCDM
and applies Eq.~\eqref{eq:rvv_o_update} to the $D$ output elements. Software
continues to own the output-buffer pointers. This boundary keeps the regular
vector update on the unchanged Spatz/RVV path and confines \texttt{OMERGE} to the
state-dependent recurrence.

\subsection{Persistent Configuration}
\texttt{OMERGE} needs a stable set of addresses and workload parameters across
tile merges. Rewriting those values for every command would move setup traffic
back into the recurring path. \texttt{OMCFG} establishes this context once per
workload; \texttt{OMERGE} then invokes one recurrence per later tile:

\begin{equation}
\underbrace{\texttt{OMCFG}}_{\text{workload-persistent context}}
\quad+\quad
\underbrace{\texttt{OMERGE}}_{\text{one invocation per merge}}.
\label{eq:cfg_merge_model}
\end{equation}

\centering
\includegraphics[width=\textwidth]{./figure/fig4.png}

Hardware toggles only the A/B scalar-state selector; software swaps the

\label{fig:programming_model}

Figure~\ref{fig:programming_model} places the four ownership classes on the
execution timeline: \texttt{OMCFG} establishes persistent context, \texttt{OMERGE} advances the
scalar state, hardware toggles the selector after successful completion, and
software updates the output-buffer pointers.

\texttt{OMCFG} shares custom-2 with \texttt{OMERGE} and selects funct3
\texttt{001}. Its I-type-like layout places the configuration identifier in
the 12-bit immediate and the value source in \texttt{rs1}. The encoding fixes
\texttt{rd} to \texttt{x0}, so Snitch creates no destination scoreboard entry
and the accelerator path returns no writeback payload. The adapter accepts
the short command only while idle and while the SMU engine is idle.

Version~1 exposes nine required persistent fields and a separate CTRL/INIT
operation, as listed in Table~\ref{tab:isa_interface}. The address fields
carry the physical TCDM
locations for the two running-state pairs, the tile-local scalar state, and
the two weight destinations. \texttt{N} supplies the scalar row bound.

The nine required fields share the canonical generated registers with the
legacy MMIO interface. An \texttt{OMCFG} field write drives the hardware-write
side of its corresponding register, so an MMIO read observes the same value.
The adapter records each field in a \texttt{9'h1FF} written mask and marks the
context dirty. A CTRL command with bit~0 set commits the context only when the
written mask contains all nine required bits. A successful commit sets \texttt{cfg\_valid} and
resets the selector to zero. A CTRL command with bit~0 clear leaves the commit
state unchanged, and rewriting any required field makes a later INIT necessary.

The v1 boundary covers the scalar recurrence context. The namespace contains no
IDs for $D$, precision or mode, tile size, output-vector addresses, stride, or
the A/B selector. The adapter fixes Mixed Scalar mode and supplies validation
constants for the engine's unused scalar-mode fields, including $D=1$ and
stride zero. Workload dimension and output addressing remain software/RVV
parameters. Reserved IDs perform no register write and invalidate readiness;
software must issue a complete INIT before a subsequent \texttt{OMERGE} can run.

\texttt{OMCFG} updates context only. It never starts the recurrence engine.
This lifetime separation places one-time configuration outside the recurring
invocation path. The evaluation therefore reports the setup window separately
from the steady-state Native Core window.

\subsection{Hardware-Maintained Dynamic State}
The configured addresses identify two physical running-state buffers, but each
successful merge changes which buffer holds the current state. A one-bit
hardware selector tracks that transition and removes per-merge address updates
from software.

The selector operates on two TCDM-resident buffer pairs:

\begin{equation}
A=(A_m,A_l),
\qquad
B=(B_m,B_l).
\label{eq:ab_state}
\end{equation}

Selector zero selects $A$ as the source and $B$ as the destination. Selector
one selects $B$ as the source and $A$ as the destination. The selector changes
the physical \texttt{m/l} addresses supplied to the SMU. The buffers stay in
TCDM and retain their contents.

Software handles the first tile as initialization. It writes the initial
running scalar state into $A$ and initializes the output buffer in software,
so no \texttt{OMERGE} runs for that tile. A complete INIT
leaves the selector at zero. The first later merge therefore reads $A$ and
writes $B$, and subsequent merges alternate the direction:

\begin{equation}
A\rightarrow B,\quad
B\rightarrow A,\quad
A\rightarrow B,\ \ldots
\label{eq:selector_sequence}
\end{equation}

The adapter commits a selector transition only when the issuing core accepts a
zero-error accelerator response. Issue and SMU start leave the selector
unchanged. An incomplete or dirty context returns a nonzero status without
asserting engine start. An SMU error also returns a nonzero status. Both cases
leave the selector at its previous value, so a failed command cannot redirect
the next successful merge.

The selector owns only the scalar $m/l$ state. Software continues to maintain
the two $D$-dimensional output-buffer pointers, and the unchanged RVV routine
performs the output update after each successful recurrence. Software also owns
tile addresses and output pointers. This ownership split gives
\texttt{OMCFG} a persistent scalar context, \texttt{OMERGE} a single recurring
operation, and RVV responsibility for dimension-dependent output state.

\section{Evaluation}

\subsection{Experimental Setup and Measurement Scope}
All results come from cycle-level simulation of the Spatz RISC-V vector
cluster. The Verilated model uses Verilator 5.034 and the default cluster
configuration with 128~KiB of 16-bank TCDM. Cycle counters bracket each
measured stage explicitly, and every matched comparison runs on the same frozen
cluster configuration and software toolchain.

N8/D32 and N16/D64 are the two anchor workloads. N24/D64 and N16/D128 test
whether the observed behavior survives a change in sequence length or output
dimension. All native-attention cases use tile size four and seed one. The
first tile initializes the running state directly and needs no merge, so a
workload with $N/4$ tiles requires

\begin{equation}
N_{\mathrm{merge}} = \frac{N}{4} - 1.
\label{eq:merge_count}
\end{equation}

That gives one merge at N8/D32, three at N16/D64, five at N24/D64, and three at
N16/D128.

The design accelerates only part of native online attention, so we report three
timing scopes. The \emph{recurrence} window covers the state-dependent update
that produces $m'$, $l'$, $w_{\mathrm{old}}$, and $w_{\mathrm{tile}}$. The
\emph{merge} window adds the corresponding RVV output update and the merge-side
orchestration. The \emph{Native Core} window adds score-tile computation,
tile-local state construction, first-tile handling, all later merges, and the
final output handling. Allocation, input generation, diagnostics, Q/K/V
loading, and linear projection stay outside all three, so none of them measures
full attention or a full model.

The comparisons form independent matched families. The first sets B2R against
Mixed Scalar SMU + RVV to isolate recurrence offload; B2R runs the recurrence
in scalar software and keeps the same RVV output update as the SMU path. The
second sets A1-MMIO against A1-ISA/\texttt{OMERGE}: both use the same SMU
arithmetic and RVV routine and differ only in how each recurrence is triggered.
The third sets MMIO-config+\texttt{OMERGE} against
\texttt{OMCFG}-config+\texttt{OMERGE}: both invoke \texttt{OMERGE} inside the
Native Core and differ only in how the one-time configuration is transported.
Full SMU/A2 appears only in a separate historical ablation.

Absolute cycle counts from different families are not a chronological
optimization trajectory, and we never read them as one. Each result is compared
only with its matched baseline from the same frozen experiment. Phase 5/6,
Phase 7, and Phase 8C use different simulator and implementation epochs, so
their absolute counts do not combine into a progressive speedup. Kept separate,
the families isolate arithmetic offload, recurring invocation, persistent
configuration, and full-offload area cost.

\subsection{HW/SW Partition Ablation}
The final architecture keeps the $D$-dimensional output update on RVV and omits
a dedicated vector datapath in the SMU. We examine this choice with a separately
frozen Full SMU/A2 experiment. This ablation predates the final \texttt{OMERGE}/\texttt{OMCFG}
implementation, so its absolute area and cycle values remain within their own
matched historical epoch.

There, selective A1 combines scalar recurrence offload with the RVV output
update, and Full SMU/A2 additionally moves the dimension-dependent output
update into the accelerator. Standalone area rises from 77,103.292 to
114,713.298 units, a 48.779\% increase. The historical mapped delay proxy also
rises, from 12.34285 to 13.20260~ns.

Full SMU/A2 is also slower than selective A1 on all three historical workloads.
These values stay out of the final native-attention results. Together with the
area comparison they support the selective partition: regular $D$-dimensional
work stays on the RVV datapath instead of being duplicated inside the SMU.

\subsection{ISA Interface Evaluation}
The ISA interface is evaluated in two stages: recurring per-merge invocation
first, then one-time workload configuration with \texttt{OMERGE} held common.

A1-MMIO and A1-ISA/\texttt{OMERGE} use the same Mixed Scalar SMU arithmetic, RVV output
routine, workload, tile size, and numerical semantics. They differ only in how
each non-first-tile recurrence is triggered. For N8/D32, the inclusive
recurrence/control window decreases from 2,069 to 848 cycles, a 59.014\%
reduction. For N16/D64, it decreases from 8,429 to 4,929 cycles, a 41.523\%
reduction.

The inclusive recurrence/control window contains issue and control activity, SMU
execution and busy time, response commit, and status consumption. It therefore
measures more than pure dispatch latency. At the merge scope, \texttt{OMERGE} reduces
cycles by 41.695\% for N8/D32 and 21.954\% for N16/D64. When the one-time ISA
setup enters the Native Core window, the reductions become 0.841\% and 0.448\%.

With \texttt{OMERGE} held common, we compare MMIO-config+\texttt{OMERGE} against
\texttt{OMCFG}-config+\texttt{OMERGE}. Both variants execute the same \texttt{OMERGE}-based Native Core.
They differ only in the transport of nine configuration fields and one INIT
operation before core execution. For N8/D32, setup decreases from 991 to 659
cycles, a 33.50\% reduction. For N16/D64, it decreases from 986 to 632 cycles,
a 35.90\% reduction. Native Core execution is identical for N8/D32 and differs
by only 12 cycles for N16/D64. Table~\ref{tab:isa_results} summarizes both

\subsection{Explicit-P Negative Control}
A last experiment asks whether the SMU is any good as a general replacement for
row-wise Softmax in an explicit probability-matrix dataflow. The surrounding
quantized-attention path is held fixed; only the explicit-P software Softmax
backend is swapped for the Mixed SMU backend.

For N8/D32, Mixed SMU increases the explicit-P Softmax window from 12,502 to
14,812 cycles, making it 18.477\% slower than software. For N16/D64, the
window changes from 48,595 to 48,534 cycles, a 0.126\% improvement. The wider
attention windows remain slightly slower with the SMU in both cases.

The five-stage Attention Total changes from 839,111 to 841,597 cycles for
N8/D32, a 0.296\% increase, and from 6,767,387 to 6,768,406 cycles for
N16/D64, a 0.015\% increase. The complete Mixed Softmax window includes $P$
initialization, SMU launch and polling, the RVV probability update, and
swap/clear orchestration. The five-stage Attention Total sums arithmetic terms;
it does not come from an independent timing counter.

These results contrast with the native online-attention results in
Section~IV-C. As a generic row-wise Softmax replacement the SMU offers no
consistent benefit. It pays off only where the hardware matches the persistent
normalized state and scalar recurrence of native online attention, with the
dimension-dependent output update left on RVV.

\section{Related Work}

\subsection{Softmax and Nonlinear Acceleration}

Once matrix multiplication is well optimized, nonlinear operators such as
exponentiation, Softmax, and GELU become the bottleneck in Transformer
workloads. Prior work attacks this at several granularities, from arithmetic ISA
extensions to dedicated nonlinear accelerators.

VEXP puts an approximate BFloat16 exponential unit inside the floating-point
unit of Snitch RISC-V cores and exposes it through scalar \texttt{FEXP} and
packed-SIMD \texttt{VFEXP} instructions \cite{wang2025vexp}. Its Softmax kernel
pairs that exponential with the existing Snitch execution mechanisms, and
reports up to 162.7$\times$ lower Softmax latency and an 8.2$\times$ gain for
FlashAttention-2 in the GPT-2 configuration. VEXP is a fine-grained approach:
it adds the costly nonlinear primitive to the programmable datapath.

SoftEx takes the other route and accelerates the whole nonlinear operator in
dedicated BFloat16 hardware \cite{belano2025softex}. Its datapath covers
approximate exponentiation, accumulation, inversion, and normalization, and
sits in a RISC-V cluster next to a matrix engine. The extended design also
supports GELU and reports up to 10.8$\times$ Softmax acceleration, which shows
what nonlinear hardware beside an already accelerated matrix path can buy.

Neither design defines the persistent normalized state and per-merge control
that native online attention relies on. The SMU works at a different
algorithmic boundary. It specializes only the state-dependent recurrence:
maximum selection, rescaling, normalization-state update, and generation of the
two merge weights. The $D$-dimensional output update stays on the RVV datapath.
As the explicit-P negative control in Section~IV-F shows, this is not meant as
a general row-wise Softmax replacement. The benefit depends on the persistent
online-merge state and the execution structure of native attention.

\subsection{RISC-V Domain-Specific Acceleration}

RISC-V's extensibility lets domain-specific hardware stay under software
control without a separate programming model. Systems so far span tightly
integrated functional-unit extensions, coprocessor-style accelerators, and
vector-processor extensions.

Spatz provides the programmable vector substrate used here: a compact RISC-V
vector processor for tightly coupled shared-memory clusters, with regular
vector execution and a comparatively small vector register file
\cite{Spatz2023}. Our design keeps that vector datapath for the regular output
update and leaves RVV execution semantics untouched.

TOP-V is another example of selective specialization \cite{chen2026topv}.
Mixture-of-Experts routing needs a branch- and dependency-heavy Top-K
operation, so TOP-V adds a configurable sorting unit to the Ara RISC-V vector
processor and exposes it as a custom \texttt{VTOPK} instruction. The reported
implementation reaches up to 5.24$\times$ over an RVV-based sort. It supports a
broader observation: operations with irregular dependency structures can
justify dedicated hardware even when the surrounding computation maps well to a
vector processor.

Cluster-local accelerators take a complementary route. RedMulE is a tightly
coupled matrix engine for floating-point GEMM and GEMM-like operations in PULP
RISC-V clusters \cite{tortorella2023redmule}. It attaches a dedicated engine to
the shared cluster memory and lets the programmable cores coordinate it.

All of these offer either a specialized primitive or a general engine. None
exposes the online-merge state or the alternating scalar-state ownership.

We apply the same heterogeneous integration model to a much smaller stateful
recurrence. The SMU issues its own TCDM requests, so standard Spatz/RVV
execution is unaffected. The custom interface separates workload-persistent
configuration (\texttt{OMCFG}) from recurring execution (\texttt{OMERGE}), and
only the alternating scalar-state selector lives in hardware. Specialization
therefore stays outside the regular vector datapath without repeated software
control on every merge.

\subsection{HW/SW Co-Design for AI Acceleration}

Efficient AI acceleration turns on how computation, memory movement, control,
and software are divided across the system. Gemmini is an open-source full-stack
DNN accelerator generator built around that principle \cite{genc2021gemmini}.
It attaches a configurable systolic array to a RISC-V host over RoCC and ships
a software stack that evaluates accelerator configurations in complete systems,
surrounding compute blocks included.

One level up in abstraction, Deeploy maps whole neural networks onto
heterogeneous RISC-V microcontrollers \cite{scherer2024deeploy}. Its compiler
emits optimized C for systems that mix RV32 processors, machine-learning ISA
extensions, and an NPU, while managing tight memory and heterogeneous compute
explicitly. The lesson is that kernels should go to the hardware whose
execution characteristics fit them best.

Both systems target whole accelerators or compiler mappings. An interface tuned
to a recurrence over persistent scalar state sits outside either abstraction.

We apply the same co-design principle at a finer granularity, inside online
attention. Software keeps score construction, tile management, first-tile
initialization, output-buffer ownership, and the regular RVV vector update.
Hardware takes only the nonlinear scalar recurrence, its persistent
configuration, and the dynamic A/B scalar-state selector. The custom hardware
thus lifts one small, dependency-heavy component off the programmable attention
path and leaves the vector execution resources in place.

\section{Conclusion}

We presented a selective HW/SW co-design for native online attention on a
RISC-V vector cluster. A cluster-local Scalar Online-Merge Unit (SMU)
specializes only the state-dependent recurrence; the Spatz/RVV datapath keeps
the regular $D$-dimensional output update. The SMU uses stage-aware mixed
precision, and the \texttt{OMCFG}/\texttt{OMERGE} interface separates
persistent configuration from recurring merge invocation, with the alternating
scalar-state selector held in hardware.

On four native workloads the design reaches 8.524--17.784$\times$ recurrence
speedup, 4.144--6.275$\times$ merge speedup, and 1.066--1.157$\times$ Native
Core speedup. It cuts standalone mapped area by 27.613\% against the legacy
scalar implementation while keeping close numerical agreement with the FP32
reference. In two measured explicit-P cases the same unit gives no consistent
benefit as a generic row-wise Softmax replacement. That negative control
supports our reading: the acceleration comes from matching the hardware to the
native online-merge dataflow.
